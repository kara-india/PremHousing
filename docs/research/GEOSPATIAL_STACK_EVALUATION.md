# PREM geospatial stack evaluation

**Phase:** 0 research; no application or database changes

**Reviewed:** 2026-11-23
**Context:** PREM Housing is a Vite/React app backed by Supabase. The repository's current data model already uses PostGIS geography for spatial fields. This is a technology evaluation, not a vendor selection or legal opinion. Prices and provider terms can change; recheck before launch.

## Recommendation

Use **MapLibre GL JS** as the web renderer, **Supabase Postgres/PostGIS** as the authoritative spatial query store for PREM listings and verified local data, and a **replaceable basemap adapter** so styles/tiles can change without rewriting listing logic. Start with a commercial tile provider on an explicitly approved commercial plan (MapTiler Cloud Flex is one viable candidate at the currently listed $30/month base; usage above included quotas is metered). Do not use MapTiler Free for public commercial launch: its terms limit that plan to non-commercial use and research/development. Keep a self-hosted/static **PMTiles** option as a later fallback for stable basemap or static layers, after source-license review and a small operational trial.

For the initial product, render verified published property points and ordinary clusters, with locality/search filters. Do not ship a market-price heatmap or forecast choropleth until PREM has sufficiently dense, provenance-reviewed and time-stamped observations. A renderer can color supplied values; it cannot establish that values are representative. Keep a clear no-data state. Consider deck.gl only if measured overlay volume or analytical interaction outgrows MapLibre's native layers. kepler.gl is best treated as an internal exploratory/research tool, not the customer-facing explorer.

| Concern | Preferred | Fallback / later option | Why |
|---|---|---|---|
| Web renderer | MapLibre GL JS | Leaflet for a simple raster/low-complexity map; Mapbox GL JS if paid vendor services/features are selected | Vector styling, data-driven layers, built-in clustering and heatmap, no renderer-imposed hosted-tile requirement. Provider and data remain independent. |
| Listing query and spatial truth | Existing Supabase PostGIS | None proposed for transactional listing data | Spatial predicates, indexed bounding-box/radius queries and controlled APIs fit mutable listings. Keep property records out of static basemap archives. |
| Optional large analytical overlays | MapLibre native sources first | deck.gl overlay after profiling | Adds capability only when required; avoid extra bundle and integration complexity in MVP. |
| Static tile archive / storage | Defer | PMTiles in range-capable object storage + CDN | One immutable archive can be read by range requests without a dedicated tile server. Updates rewrite the archive; this is not a live listings database. |
| Grid aggregation | Locality/admin polygons when authoritative; otherwise ordinary clusters | H3 when a verified analytical use case and privacy policy exist | Cells can be useful for aggregation, but are not official neighborhoods and do not by themselves make small-sample data safe. |

## Keep the roles distinct

1. **Renderer:** MapLibre GL JS, Leaflet, Mapbox GL JS or deck.gl draws a view in the browser. Renderer license does not grant map data, geocoding or tile-service rights.
2. **Basemap data and tile service:** MapTiler, Mapbox, self-hosted OSM-derived tiles, or another vendor supplies cartographic tiles/styles. Their product terms, pricing, attribution, caching, quotas and coverage govern their use. OSM's public raster tile endpoint is not a production unlimited tile service.
3. **PREM business data:** Postgres/PostGIS stores mutable listings, approved points, verified locality boundaries, provenance, observation time and access rules. Read only published and authorized data through narrow query contracts. Do not put private contact/lead/staff fields into map responses.
4. **Static storage:** PMTiles is a read-only tiled archive format, not a renderer, source-data license, database or hosted service. An object store/CDN hosts bytes; range requests and CORS must work. Every included layer retains its own licensing and attribution requirements.
5. **Geospatial index/aggregation:** H3 maps coordinates to hierarchical hexagonal indices and can support group-by/neighbor operations. It is not a basemap, renderer, address geocoder or authoritative locality boundary.
6. **Geocoding and routing:** Separate APIs/products with their own India coverage, attribution, retention and price terms. None is selected by this recommendation. Never infer routable access or travel times from straight-line distance.

## Provider, data and India-specific risks

- **No national-coverage assumption:** Global basemap availability does not prove street, building, road-access, POI, address or locality-boundary completeness in Mira-Bhayandar. OSM completeness varies locally; provider styling may hide available features. Test representative Mira Road, Bhayandar, Kashimira, Dahisar-border and service-area cases against field/official references. Label locality boundaries as approximate unless their source and legal status are verified.
- **Writing/transliteration:** Check label coverage and legibility for English, Hindi and Marathi, including local spelling variants. A blank label is not evidence that a locality or service is absent.
- **Geocoder uncertainty:** Address formats, landmarks, informal names and transliteration can produce ambiguous matches. Store normalized input, selected result/provider, confidence and correction workflow, subject to provider retention rules. Do not silently publish low-confidence points or reveal exact private residential points.
- **Routes:** Routing quality and availability for India, traffic and walking/transit modes are provider-specific. Validate practical local routes and terms separately. Keep route-based claims out of market predictions unless validated against real route service and clearly qualified.
- **Data rights:** OSM-derived tiles/data may carry ODbL obligations; third-party POI, boundary, real-estate, scraped or contributed data may have distinct conditions. Record provenance, source URL/vendor, access date, license/terms, permitted public uses, freshness and attribution. No scraped source is assumed licensed merely because accessible.
- **Privacy:** Map locations can reidentify an occupant or listing. Publish only approved listing points, generalize exact coordinates where required, exclude private fields, suppress small aggregates, and prevent unauthorized users from testing arbitrary coordinates for existence.
- **Reliability/cost:** Tile rendering can be cheap at low traffic but vendor sessions, API requests, geocoding, storage GETs, egress and paid support are separate. Instrument map initializations, tile/API request volume, failures and costs; alert before quota thresholds.
- **Mobile:** WebGL GPU memory, large GeoJSON and marker DOM nodes can degrade lower-end Android devices. Prefer vector sources/layers and clusters, bound features by viewport/zoom, lazy-load the map, offer list/search without map, and test actual target devices and weak networks.
- **Lock-in:** Keep domain data in GeoJSON/WGS84 and PostGIS, preserve provider-neutral feature IDs/properties, separate styles from product UI, store attribution text and data provenance, avoid provider-specific place IDs as PREM primary keys, and make geocoder/routing adapters replaceable.

## Cost and selection notes

MapTiler Cloud currently lists Free at $0 for testing/personal/noncommercial use and Flex at $30/month, including 25k sessions and 500k API requests per month; excess is listed at $2.50/1k sessions and $0.15/1k API requests. Taxes/VAT are excluded. Confirm how the chosen MapLibre integration is metered, whether intended commercial use and relevant attribution/style meet the account terms, and estimate actual tile requests before procurement. This is a candidate, not owner approval or a committed selection. Mapbox has distinct map-load/API meters; PostGIS is included as database software but managed database compute is billable; PMTiles shifts costs to storage requests/egress and maintenance rather than eliminating them.

Given the project direction's constraint to avoid an unapproved paid map plan, implementation can be structured now around a replaceable basemap source, but production map credentials should remain unset until the owner chooses a commercial plan or explicitly adopts a properly licensed self-hosted dataset. Never ship a dev/demo tile endpoint as a production SLA.

## Phase 0 acceptance criteria before Phase 1 map code

- Product owner selects commercial basemap provider/plan or self-hosted data source, budget cap and billing-alert owner.
- Product owner approves attribution placement, supported language labels, and whether the map is optional/lazy-loaded on first visit.
- PREM identifies valid, licensed India-local boundary/POI sources and the permitted uses of current listing coordinates.
- Backend contract returns only published, authorized map fields with bounded viewport/filter constraints; private exact location policy is documented.
- No-data behavior for market layer and distinction between listings count, observations and predictions are approved.
- Provider selection remains replaceable; credentials are origin-restricted and stay in appropriate environment configuration.
